# K-0.2-HARDEN-001 — DownloadManager: surface fatal errors from download virtual threads

**Phase:** 0.2 — CLI & Persistence
**Type:** Hardening
**Status:** DONE
**Date:** 2026-11-11
**Depends on:** K-0.2-CLI-HANG-001

## Background

K-0.2-CLI-HANG-001 found that `DefaultDownloadManager.runDownload` catches `Exception`, not
`Throwable`. A `LinkageError` (e.g. `UnsupportedClassVersionError`) thrown during
`strategy.download(...)` escapes the catch, kills the download virtual thread silently, and
leaves any waiting CLI latch blocked indefinitely. No `DownloadFailedEvent` is emitted.

This is a production robustness gap: any `Error` on a download VT — including
`OutOfMemoryError`, `StackOverflowError`, or future preview-API misconfigurations — becomes
invisible to callers and produces a silent hang rather than a clear failure.

## Objective

Change the `catch (Exception e)` block around `strategy.download(task, context, this::emit)` in
`DefaultDownloadManager.runDownload` to `catch (Throwable t)` so that:

1. Any `Error` on the download VT is captured and emitted as a `DownloadFailedEvent`.
2. Callers (CLI, UI, tests) always receive a terminal event and do not hang.
3. After emitting the event the `Error` is re-thrown so the VT's uncaught-exception path
   still surfaces it (preserving the existing behaviour for legitimate fatal JVM errors).

## Scope

- `katabasis-core/src/main/java/jsanca/katabasis/core/api/manager/DownloadManagers.java`
  — `DefaultDownloadManager.runDownload` only.
- Update the existing `DownloadManagerTest` or add a targeted test that injects a strategy
  throwing `Error` and asserts that `DownloadFailedEvent` is emitted.

## Constraints

- Do not change any other catch blocks or exception-handling policy.
- Do not modify the CLI, storage, or HTTP strategies.
- If re-throwing the `Error` after emitting the event causes any existing test to fail,
  document the behaviour change and ask before proceeding.
