# K-0.2-T05-HARDEN-001 — DownloadListCommand Hardening

## Objective

Close three correctness gaps in `DownloadListCommand` identified after K-0.2-T05:

**A — Effective Concurrency**: Demonstrate via a barrier-based CLI-layer test that `maxConcurrentDownloads` limits parallel downloads as configured.

**B — Submission Failures & CountDownLatch Safety**: Guard against two defects:
1. Synchronous `RuntimeException` from `manager.download()` (e.g., `DownloadRejectedException` when manager is closed) propagates out of the submission loop uncaught, bypassing `latch.await()` and producing a confusing exit rather than clean error accounting.
2. Duplicate terminal events for the same download ID can overwrite `outcomes` entries and call `latch.countDown()` twice, corrupting outcome tallies.

**C — Destination Filesystem Safety**: `Files.exists(target)` follows symlinks; a symlink to a nonexistent target returns `false`, bypassing pre-validation and allowing the core layer to write through the symlink. Fix: check `Files.isSymbolicLink(target)` before `Files.exists(target)`.

## Out of Scope

- TOCTOU race between `Files.exists` and core file creation — documented as known limitation, not fixed here.
- Core `HttpDownloadStrategy` does not use `CREATE_NEW` — documented as known limitation, not fixed here.
- `K-0.2-HARDEN-001`: changing `catch (Exception)` to `catch (Throwable)` in `DefaultDownloadManager.runDownload` — separate pending task.
