# K-0.1-T07 Report — Segmented HTTP Resource Integrity & Capability Negotiation

## Summary

Implemented two-stage HTTP range-capability negotiation and strict per-segment integrity
validation. The orchestrator now probes twice before committing to segmented mode: a HEAD
request to discover `Accept-Ranges` and a strong ETag, then a lightweight `GET bytes=0-0`
to confirm the server honours ranges in practice. Without a strong ETag or when either probe
fails, the orchestrator falls back silently to `HttpDownloadStrategy`.

Segmented downloads now carry end-to-end integrity guarantees: each chunk request includes
`If-Range` and `Accept-Encoding: identity`; every 206 response is validated against the
established `ResourceIdentity` before a single byte is written; byte overflow past the
assigned range boundary is detected before each `FileChannel.write()`; and truncated
delivery is caught after the read loop exits.

## Design Decisions

**Strong ETag required for segmented mode.** Range reassembly is safe only when we know all
chunks belong to the same resource representation. Weak ETags (`W/"…"`) are not suitable for
`If-Range` per RFC 7232 §3.3 and are discarded. If neither probe returns a strong ETag, the
orchestrator falls back to single-stream regardless of `Accept-Ranges`.

**Two-stage probe.** HEAD determines capability; `GET bytes=0-0` confirms it. A server can
advertise `Accept-Ranges: bytes` but still return 200 for actual range requests (CDN
misconfiguration, transparent proxies). The range probe catches this before the segmented
strategy commits.

**`ResourceIntegrityException extends IOException`.** This makes it automatically
non-retryable via the existing `HttpFailureClassifier` with no code changes. The catch block
in `doChunkAttempt` rewinds `totalDownloaded` and rethrows, which propagates through
`RetryExecutor` without retry and surfaces as a `DownloadFailedEvent`.

**Byte overflow check before write.** The check `position + bytesRead > chunk.end() + 1`
runs before `FileChannel.write()` so a buggy or malicious server cannot overwrite another
segment's data in the shared file channel.

## Architectural Notes

The `ResourceIdentity` record is the single source of truth for content length and ETag
across the entire segmented download lifecycle — from probe, through per-chunk request
construction (`rangeRequestWithValidator`), to per-segment response validation
(`validateSegmentResponseHeaders`). This eliminates the possibility of scope-local `long`
drift or ETag inconsistency between segments.
