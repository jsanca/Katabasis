## Status

Complete

## Objective

Correct inaccurate guarantees in ADR-002 and reconcile ADR-004 with the current Java 27
implementation state. No production code changes.

---

## ADR-002 Corrections

### 1. Durability — rewritten

The previous text made two incorrect claims:

**Claim 1:** "Journaling filesystems preserve rename semantics across power failure. The most
recent committed checkpoint survives."

**Why incorrect:** Journaling protects filesystem _metadata_ (directory entries), not file
_content_. File content without `fsync` may be lost on power failure even on ext4/APFS/ZFS.
Only the rename operation itself (directory-entry atomicity) benefits from journaling.

**Claim 2:** "A checkpoint persisted more than one writeback window before process termination
will survive… journaling-filesystem power failures."

**Why incorrect:** "Writeback window" is an approximate OS heuristic (typically 5–30 s), not
a filesystem guarantee. Without `fsync`, there is no way to bound when content reaches durable
storage on a standard filesystem configuration.

**Replacement:** The ADR now distinguishes five durability levels explicitly:

1. OS write API accepted (OutputStream / FileChannel) — implemented
2. OS flush (page cache visible to other processes) — implicit for FileChannel; explicit flush only on completion for OutputStream
3. Process-crash resilience — yes (OS page cache survives `kill -9`)
4. Kernel/OS-crash resilience — **not guaranteed** (no `fsync`)
5. Power-loss durability — **not guaranteed** (no `fsync`)

Phase 0.2 guarantee is now stated correctly: checkpoints survive process termination (including
`kill -9`) and are protected from partial-write visibility. They are not guaranteed to survive
kernel crash or power failure.

### 2. Atomic visibility — made conditional

The previous text asserted unconditional atomic visibility. The fallback path (`REPLACE_EXISTING`
when `ATOMIC_MOVE` is unsupported) is non-atomic. The ADR now states:

- Atomic visibility holds when `ATOMIC_MOVE` succeeds.
- On non-atomic fallback: a concurrent reader may observe a partially written or zero-length file.
  The store tolerates this via `CodecException` → absent result (no data corruption, but
  visibility is not guaranteed).

### 3. `confirmedBytes` semantics — new subsection

The previous ADR did not define what `confirmedBytes` means in terms of write pipeline layers.

Actual semantics (verified against implementation):
- **Single-stream:** bytes passed to `OutputStream.write()` — may be in JVM heap buffers.
  `flush()` is called only at download completion, not at checkpoint time.
- **Segmented:** bytes accepted by `FileChannel.write()` — in OS page cache, not durable.

Recovery invariant added: file length alone is insufficient to validate segmented content.
Concurrent VT writes produce a sparse file; each segment's confirmed prefix must be validated
independently. ETag revalidation required before reusing any range.

### 4. Shutdown versus explicit cancellation — new subsection

The ADR now documents the `shutdownCancelledIds` mechanism implemented in `DownloadManagers`:

- `DownloadManager.close()` suppresses `DownloadCancelledEvent` for downloads it cancels.
- The coordinator receives no cancellation event; manifests remain with `IN_PROGRESS` status.
- Downloads interrupted by shutdown are recoverable at next process start.

Two limitations now explicitly recorded:
- **Close ordering requirement:** caller must close `CheckpointCoordinator` after
  `DownloadManager.close()` returns. Closing in the wrong order loses the final flush.
- **Executor timeout:** `VirtualThreadDownloadExecutor` waits only 10 s for tasks to terminate.
  Tasks that do not respond within that window may still be running when the coordinator is
  closed, losing their final checkpoint.

### 5. T10 metadata integration — Option A rejected, Option B recommended

Previous ADR marked enriched public events as "preferred". This was incorrect for segmented
downloads.

**Option A rejected:** concurrent VTs each emit `DownloadProgressEvent` after every buffer
write with no barrier between them. A `List<SegmentSnapshot>` assembled from an event handler
captures an inconsistent mid-flight state. Additionally, per-event list allocation creates GC
pressure under high-throughput downloads.

**Option B recommended:** define a `CheckpointSource` interface in `katabasis-core` internal
packages. Each executing strategy (or its owning task) implements it and exposes
`DownloadSnapshot buildSnapshot()`. The coordinator calls this at flush time under the
strategy's own synchronization, producing a consistent snapshot. This approach:
- Avoids event API changes
- Avoids per-event allocations
- Extends naturally to future FTP/S3 strategies (each provides its own `CheckpointSource`)
- Keeps HTTP-specific classes internal

### 6. T11 recovery precondition — fixed

Previous condition `confirmedBytes > 0` as a recovery criterion was removed. A snapshot with
`confirmedBytes == 0` is recoverable (re-downloads from byte 0); it is merely equivalent to a
fresh download. The actual recovery precondition is: partial file exists and its size ≥
`confirmedBytes`.

## ADR-004 Corrections

### Java 25 → Java 27

Context section updated: project migrated to Java 27 (K-JAVA27-001). Historical reference to
Java 25 preserved as context; all JPMS constraints continue to apply.

### CLI stub description removed

The opening sentence "is a stub module that must become a functional CLI" was historical.
`katabasis-cli` is now fully implemented through K-0.2-T07.

### Subcommand references corrected

Previous text: "K-0.2-T04 `download`, K-0.2-T06 `cancel`, K-0.2-T07 `list`"
Actual roadmap: T04=download, T05=download-list, T06=config options, T07=interactive lifecycle.
Replaced with a current-state table showing the four implemented areas.

### Java 27 / preview-feature note added

picocli 4.7.6 has been verified against Java 27. The distinction between CLI source (no preview
APIs, no compile-time `--enable-preview`) and test runtime (requires `--enable-preview` to load
core preview classes) is documented.
