# K-0.2-T03 — DownloadManager Lifecycle Engineering Report

## Summary

Added `AutoCloseable` with graceful shutdown to `DownloadManager`. The implementation uses a
three-state lifecycle, a `ReentrantReadWriteLock` admission gate, `CountDownLatch`-based
concurrent-closer coordination, and a `ConcurrentHashMap`-backed set to suppress
`DownloadCancelledEvent` for downloads stopped by shutdown.

## Notable Decisions

**Write lock scope is narrow**: The write lock in `close()` is held only while sweeping the registry
and signalling cancellation tokens. `executor.close()` (which awaits termination) runs outside
the lock. This prevents `cancel()`, `pause()`, and `resume()` from being blocked during the
10-second drain window.

**No `shutdownNow()`**: Virtual threads cannot be safely interrupted mid-write without risking
partial files. The 10-second `awaitTermination` bound is the practical limit. For stalled HTTP
reads, `HttpTimeoutConfig.readInactivityTimeout` is the appropriate tool.

**`DownloadCancelledEvent` suppression uses a set, not a flag**: A per-download-ID set rather than
a single boolean allows mixed operation: some downloads may be user-cancelled and some
shutdown-cancelled concurrently during the drain window, with correct per-download event
suppression.

## Architecture Questions / Findings

**K-0.2-T10 hook point**: The `close()` method in `DefaultDownloadManager` now has a natural
checkpoint for flushing `CheckpointCoordinator` before calling `executor.close()`. K-0.2-T10
should wire persistence state flush between the write-lock release and the executor drain.

**`DownloadExecutorsTest` relies on the executor being alive**: The `DownloadExecutorsTest` tests
the `VirtualThreadDownloadExecutor` directly. After this change, those tests continue to pass
because `close()` is only called by `DefaultDownloadManager`; the test does not call it.

**`stallForever` in test server**: Scenario 11 uses a server-side 60-second sleep in the GET
handler to simulate a hung connection. The `stallForever` flag causes the server to accept the
connection (so the download starts and emits `DownloadStartedEvent`) but never complete the
response. The CancellationToken detected during the 10-second `awaitTermination` does not
interrupt the network read because virtual threads do not support `Thread.interrupt()` on blocking
socket I/O. The `awaitTermination` timeout fires, `close()` returns, and the test verifies the
15-second `assertTimeout` bound holds.
