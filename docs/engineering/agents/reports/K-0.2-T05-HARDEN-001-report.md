# K-0.2-T05-HARDEN-001 — DownloadListCommand Hardening Report

## Status

Complete

## Objective

Close three correctness gaps in `DownloadListCommand` found during post-T05 adversarial review: concurrency demonstration (A), latch safety under rejection and duplicate events (B), and symlink bypass in pre-validation (C).

## Findings

### A — Effective Concurrency

**Result: PASS (no code change required).**

`VirtualThreadDownloadExecutor` submits all download VTs immediately but gates each on `semaphore.acquire()` before any HTTP activity begins. The semaphore permits equal `maxConcurrentDownloads`. This correctly limits inflight downloads at the manager level, which is exactly where the CLI's `DownloadListCommand` submits work.

A barrier-based integration test (TC-HARDEN-A-001) demonstrates this at the CLI layer: 4 URLs with `maxConcurrentDownloads=2`, server holds requests at a `CountDownLatch`; test asserts exactly 2 are inflight when the barrier is reached and that `barrierPeak ≤ 2` throughout.

### B — Submission Failures & CountDownLatch Safety

Two defects confirmed and fixed.

**B1 — Synchronous rejection uncaught.**

`manager.download()` throws `DownloadRejectedException` (a `RuntimeException`) when the manager lifecycle is not `OPEN`. The submission `for` loop had no `try/catch`, so the exception would propagate past `latch.await()`, leaving the latch uncounted and causing a confusing picocli execution exception exit rather than a clean `exit 1`.

Fix: wrap each `manager.download()` call in `try/catch (RuntimeException e)`. On catch: print `"  Rejected: <filename> — <message>"` to `err`, `rejectedCount.incrementAndGet()`, `latch.countDown()`. The final `failed` count is `outcomes_failed + rejectedCount.get()`.

TC-HARDEN-B-001 verifies: manager pre-closed before command runs → `exit 1`, non-blank stderr, no hang.

**B2 — Duplicate terminal event overwrites outcome.**

`outcomes.put(id, value)` unconditionally overwrites on a second event for the same ID, and `latch.countDown()` is called again (harmless per `CountDownLatch` semantics, but outcome tally is corrupted). With N=1 this is unobservable; with N>1 and a buggy strategy firing two events, an `exit 0` could become `exit 1`.

Fix: replace `outcomes.put(id, value)` with `outcomes.putIfAbsent(id, value)`. Only when `putIfAbsent` returns `null` (first assignment) are the log line and `latch.countDown()` executed.

TC-HARDEN-B-002 verifies: fake `DownloadManager` fires two `DownloadCompletedEvent`s for the same ID → `exit 0`, stdout reports `"1 completed"` and `"0 failed"`.

### C — Destination Filesystem Safety

**Defect confirmed and fixed.**

`Files.exists(target)` follows symlinks. A symlink to a nonexistent target returns `false`, so the pre-validation loop accepted it, and `HttpDownloadStrategy.download()` would write through the symlink to its target path, violating the intent of the existence check.

Fix: add `else if (Files.isSymbolicLink(target))` before `else if (Files.exists(target))` in the resolution loop. `Files.isSymbolicLink` does **not** follow symlinks — it returns `true` for the link itself regardless of whether the target exists. Error message: `"destination is a symbolic link: <filename>"`.

**Known limitations documented (not fixed here):**
- TOCTOU race between `Files.exists` check and core file creation is inherent to the two-phase design. Would require `StandardOpenOption.CREATE_NEW` in `HttpDownloadStrategy` to close atomically — out of scope.
- `HttpDownloadStrategy` uses `Files.newOutputStream` with default options (`CREATE + TRUNCATE_EXISTING`), not `CREATE_NEW` — a separate core-layer concern tracked under potential future hardening.

TC-HARDEN-C-001 verifies: symlink to nonexistent target → `exit 1`, stderr contains `"symbolic link"`, symlink still present and target not created.
