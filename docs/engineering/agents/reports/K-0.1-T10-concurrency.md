## 1. Objective

Verify that Katabasis correctly manages concurrent downloads from multiple URLs, including the
interaction between download-level scheduling, segment-level parallelism, retries, cancellation,
and resource limits.

---

## 2. Concurrency Model Assessment

A survey of `DownloadExecutors.java`, `DownloadScheduler.java`, `ExecutionSlotController.java`,
and `QueuedDownloadTask.java` found the following:

| Component | Status | Role |
|---|---|---|
| `VirtualThreadDownloadExecutor` | Active | Virtual-thread executor + `Semaphore(maxConcurrentDownloads)` |
| `DownloadScheduler` | Empty placeholder | No logic |
| `ExecutionSlotController` | Empty placeholder | No logic |
| `QueuedDownloadTask` | Empty placeholder | No logic |

The only real concurrency control mechanism is the `Semaphore` in `VirtualThreadDownloadExecutor`.
It is acquired before `task.run()` and released in `finally`. Segment-level parallelism is handled
separately inside `SegmentedHttpDownloadStrategy` via `StructuredTaskScope`.

**Paused-download policy:** A paused download blocks in `PauseCoordinator.awaitIfPaused()` while
holding its semaphore permit. It is "active" for scheduling purposes; queued downloads behind it
cannot start until the paused download is resumed and completes (or is cancelled), freeing the permit.

**URL list ingestion:** No batch API exists. Callers submit individual `DownloadRequest` objects.
Queue depth is unbounded — the virtual-thread executor accepts all submitted tasks immediately,
but only `maxConcurrentDownloads` can hold the semaphore at once.

## 3. New Tests — `DownloadManagerConcurrencyTest`

10 new integration tests in `jsanca.katabasis.core.api.manager.DownloadManagerConcurrencyTest`.
Every test drives downloads through `DownloadManagers.createDefault(DownloadConfig)`.

### In-process server

A single `TestHttpServer` class handles HEAD, full GET (single-stream), and range/chunk GET
(segmented). Key features:

- **Gate mechanism** — `installGate(n)` installs a `CountDownLatch` barrier that holds all GET
  responses until `releaseGets()` is called. `awaitGetsAtGate(n, timeout)` blocks the test thread
  until exactly `n` GETs are blocked at the gate. This enables deterministic concurrency-limit
  assertions without timing dependencies.
- **Peak counter** — `peakGets` tracks the maximum number of concurrently active GETs observed.
- **Chunk counter** — `chunkRequests` counts range GET requests for segment-count verification.
- **Failure scripting** — `failFirstNNonHeadRequests(n, code)` returns a configured error for the
  first `n` non-HEAD requests.
- **Throttle** — `throttleMs` injects a delay per GET for controlled timing in ordering tests.

### Test methods and scenario coverage

| Test | Scenario |
|---|---|
| `multipleSuccessfulSingleStreamDownloadsAllComplete` | A: 4 single-stream downloads, all complete, correct content |

## 4. Notable Findings

- **Paused-permit policy confirmed**: Scenario G proved that with `maxConcurrentDownloads=1`, a
  paused download blocks a second download from making any HTTP requests. The second download's
  `DownloadStartedEvent` does not appear until the first is resumed, completes, and releases its
  permit. This is the expected policy (paused = still holding its slot).

- **Failed download releases permit**: Scenario I confirmed that a permanently-failed download
  (500 with no retry) releases its semaphore permit in `finally`, allowing the next queued download
  to proceed. No permit leak was observed.

- **Cancelled download releases permit**: Implicit in Scenario F — the cancelled download's
  virtual thread completes (with `CancelledException`), the `finally` block in `VirtualThreadDownloadExecutor`
  releases the permit, and the two non-cancelled downloads complete normally.

- **No URL list batch API exists**: The scheduler infrastructure (`DownloadScheduler`,
  `ExecutionSlotController`, `QueuedDownloadTask`) is entirely placeholder. All batching is implicit:
  callers submit individual `DownloadRequest` objects; the semaphore provides the only ordering.

- **Existing `DownloadExecutorsTest` is timing-based**: The existing `shouldRespectConcurrencyLimit`
  test uses `Thread.sleep(200)` and asserts a minimum elapsed duration. The new gate-based approach
  in `DownloadManagerConcurrencyTest` is strictly superior for determinism.
