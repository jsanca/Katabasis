# K-0.1-T03C — FileDownloadStateStore Implementation — Report

## Status

Complete

## Summary

Implemented a thread-safe, durable, filesystem-backed `DownloadStateStore` and event-driven `CheckpointCoordinator`. 119 tests pass across both modules.

## Domain additions (katabasis-core)

### `SegmentSnapshot` (api/model)
Immutable record for a single segment's download state: `index`, `startByte`, `endByte`, `confirmedBytes`. Compact constructor validates range invariants.

### `DownloadSnapshot` (api/model)
Recoverable domain record separate from `DownloadTaskSnapshot` (the live runtime view). Fields:

| Field | Type | Notes |
| --- | --- | --- |
| `downloadId` | `String` | stable identifier |
| `sourceUri` | `URI` | original source |
| `targetPath` | `Path` | final destination |
| `partialPath` | `Path` (nullable) | in-progress file; falls back to `targetPath` |
| `etag` | `String` (nullable) | strong ETag for revalidation |
| `expectedTotalBytes` | `long` | `-1` if unknown |
| `confirmedBytes` | `long` | durably written bytes |
| `status` | `DownloadStatus` | state at checkpoint time |
| `segments` | `List<SegmentSnapshot>` | empty for single-stream |
| `createdAt` | `Instant` | submission time |
| `checkpointAt` | `Instant` | when this snapshot was taken |

`isRecoverable()` returns `true` for `IN_PROGRESS` and `PAUSED`.

### `DownloadStateStore` (api/manager)
Fully defined with 4 methods: `save`, `findById`, `findRecoverable`, `delete`. No JSON framework types anywhere in the interface.

### `DownloadConfig`
Added `checkpointInterval: Duration` (default `Duration.ofSeconds(5)`). Compact constructor validates positive. Builder defaults to 5 seconds. `copyOf()` updated to propagate the field. All existing tests continue to pass via `DownloadConfig.defaultConfig()`.

## Implementation (katabasis-storage-json)

### `FileDownloadStateStore` (internal/store)
One `.json` file per download in the configured directory. Per-download `ReentrantLock` serializes concurrent saves for the same ID.

**Atomic write:** `Files.write` to `<id>.json.tmp`, then `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`. On `AtomicMoveNotSupportedException`: non-atomic replace + explicit warning log. No silent fallback.

**Revision:** reads the existing document's revision before each `save()` and increments it. Corrupt existing files reset to revision 0.

**`findRecoverable()`:** lists `.json` files, decodes each, filters for `isRecoverable()`. Corrupt files are silently skipped with a log warning.

**Multi-process:** not supported. Documented in class Javadoc.

### `CheckpointCoordinator` (api)
Registers a `Consumer<DownloadEvent>` via `DownloadManager.addListener`. Maintains a `ConcurrentHashMap<String, DownloadSnapshot>` of latest pending state. Single daemon `ScheduledExecutorService` for periodic flushing.

| Event | Action |
| --- | --- |
| `DownloadStartedEvent` | add to pending |
| `DownloadProgressEvent` | update pending (coalesces) |
| `DownloadPausedEvent` | update pending + immediate save |
| `DownloadCompletedEvent` | remove from pending + delete from store |
| `DownloadCancelledEvent` | remove from pending + delete from store |
| `DownloadFailedEvent` | remove from pending + save with FAILED status |

`close()` cancels the timer, deregisters the listener, flushes remaining pending snapshots.

**Limitation at this scope:** snapshots are built from public event data only. Segment boundaries, ETag, and partial file path are not populated. These require access to `DownloadTask` internals (K-0.2 scope).

### `DownloadStateStores` (api)
Factory with `fileStore(Path)` and `fileStore(Path, codec)` overloads. Callers receive `DownloadStateStore` interface type — concrete class never leaks.

## Durability ordering (documented)

1. HTTP strategy writes and flushes bytes to the partial file.
2. `CheckpointCoordinator` calls `DownloadStateStore.save()` with the last-known confirmed byte count.
3. `FileDownloadStateStore.save()` atomically replaces the manifest.
4. The revision is incremented on each successful write.

**Note:** `fsync` on the directory entry is not performed. Journaling filesystems (ext4, APFS) preserve rename atomicity. On non-journaling filesystems, a power failure during rename may lose the most recent checkpoint but cannot corrupt the previous one — the `.tmp` approach ensures the target is always a complete document.

## Open Items

- Segment boundaries and ETag in snapshots require `DownloadTask` internal access — K-0.2 scope.
- `findById` on a corrupt file silently returns empty; a future `findByIdOrThrow` variant may help callers distinguish "not found" from "corrupt".
- `DownloadConfig.checkpointInterval` is not yet consumed by any wired component — `CheckpointCoordinator.create(manager, store, config.checkpointInterval())` is the caller's responsibility (K-0.2 wiring task).
