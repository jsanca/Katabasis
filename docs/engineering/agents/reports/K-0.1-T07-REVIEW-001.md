## Executive summary

The T07 implementation delivers all stated acceptance criteria. ETag/If-Range mismatches, Content-Range inconsistencies, byte overflow past a segment boundary, and truncated segments all produce exactly one `DownloadFailedEvent` whose `cause()` is a `ResourceIntegrityException`, the partial file is deleted, and the integrity failures are not retried. HEAD/range-probe reconciliation falls back to single-stream when ETags disagree, when the server returns 200/416 for a `bytes=0-0` probe, when Content-Range is absent or inconsistent, or when no strong validator is available. The orchestrator fails safely over to `HttpDownloadStrategy` on probe-transport errors.

One real latent defect (partial `FileChannel.write` return value) and one minor contract gap (incomplete strong-ETag syntactic check) were identified. Neither blocks T08: the partial-write issue is extremely unlikely to manifest on local disk FileChannels in practice and does not undermine the T07 invariants when it does not occur; the ETag issue affects header parsing robustness only.

**Recommendation: ACCEPT WITH FOLLOW-UPS.**

## Findings

### RIV-001 — `FileChannel.write(ByteBuffer, long position)` return value is ignored

- **Severity:** Medium
- **Affected file:** `katabasis-core/src/main/java/jsanca/katabasis/core/internal/http/SegmentedHttpDownloadStrategy.java`, line 250 (`doChunkAttempt`, read/write loop)
- **Expected behavior:** The write loop must persist exactly `bytesRead` bytes at `position` before advancing `position` and the progress counters. `FileChannel.write(ByteBuffer, long)` is contractually permitted to return fewer bytes than the buffer's remaining; the call must be looped until the buffer is drained, and the segment-completion check (`validateSegmentByteCount`) must reflect bytes actually written, not bytes read from the socket.
- **Actual behavior:** The channel write is made once per iteration and its return value is discarded:
  ```java
  channel.write(ByteBuffer.wrap(buffer, 0, bytesRead), position);
  position += bytesRead;
  attemptBytes += bytesRead;
  ```
  If the channel writes fewer bytes than `bytesRead`, (a) `position` advances past the last persisted byte so subsequent writes leave a hole in the file, (b) `attemptBytes` and `totalDownloaded` over-count, and (c) `validateSegmentByteCount(position - chunk.start(), chunk)` passes because `position` is derived from `bytesRead`, not from bytes persisted. A silently incomplete segment can therefore reach `onComplete`.
- **Evidence:** The javadoc for `FileChannel.write(ByteBuffer, long)` explicitly states the return value "may be less than" the number of bytes requested; the same loop idiom in `HttpDownloadStrategy.doDownload` uses `OutputStream.write(buffer, 0, bytesRead)` which is defined to write all bytes, so the hazard is specific to the segmented strategy. No test covers a partial channel write (the integrity tests use the default file channel against local tmp directories where short writes are rare in practice).
- **Root cause:** FileChannel's write-at-absolute-position contract was treated as "write all or throw," matching the OutputStream contract rather than the actual FileChannel contract.
- **Minimal corrective recommendation:** Wrap the write in a drain loop and derive the advance from bytes actually written:
  ```java
  final ByteBuffer bb = ByteBuffer.wrap(buffer, 0, bytesRead);
  long written = 0;
  while (bb.hasRemaining()) {
      written += channel.write(bb, position + written);
  }
  position += written;
  attemptBytes += written;
  ```
  Progress accounting (`totalDownloaded.addAndGet`) and the post-loop `validateSegmentByteCount` should both be fed from `written`.
- **Regression test recommendation:** Add a unit test that wraps a real `FileChannel` (or uses a decorated `FileChannel` test double) which forces one short write per iteration; assert the destination file has the full expected byte content and the strategy emits a single `DownloadCompletedEvent` with `totalBytes == contentLength`.

### RIV-002 — `extractStrongETag` accepts syntactically malformed ETag values

- **Severity:** Low
- **Affected file:** `katabasis-core/src/main/java/jsanca/katabasis/core/internal/http/HttpRangeSupport.java`, lines 387-391
- **Expected behavior:** A strong ETag must start AND end with an unescaped double-quote (per RFC 7232). Values such as `"abc` (unterminated) or `abc"` (no leading quote) should be rejected and treated as absent.
- **Actual behavior:** Only the leading-quote check is enforced:
  ```java
  return response.headers().firstValue("ETag").filter(etag -> etag.startsWith("\""));
  ```
  A pathological `ETag: "abc` would be propagated as the `If-Range` validator. Most servers will then fail with 400/416, which is handled, but it widens the set of inputs that could trigger an integrity failure instead of a clean fallback.
- **Root cause:** Validator intentionally rejects weak (`W/`) ETags but did not add a closing-quote check.
- **Minimal corrective recommendation:** Tighten the predicate to `etag -> etag.length() >= 2 && etag.startsWith("\"") && etag.endsWith("\"")`.
- **Regression test recommendation:** Add a `HttpRangeSupportTest` case where the server emits `ETag: "unterminated` and assert `extractStrongETag` returns `Optional.empty()`.

### RIV-003 — Range-probe 200 response body fully buffered (informational)

- **Severity:** Low (informational — not a defect)
- **Affected file:** `katabasis-core/src/main/java/jsanca/katabasis/core/internal/http/HttpRangeSupport.java`, line 168-169 (`rangeProbe`)
- **Observation:** When the server ignores the `Range: bytes=0-0` header and returns 200 with the full body, the probe uses `BodyHandlers.ofByteArray()` and buffers the entire response before falling back. For very large resources this is wasted bandwidth and memory. No correctness consequence — the test `rangeProbeReturnsFallbackWhenServerIgnoresRangeAndResponds200` passes and `HttpClient` closes the underlying connection — but `BodyHandlers.ofByteArrayConsumer` with an early-abort would be gentler.
- **Recommendation:** Track as a non-blocking follow-up; current behavior is acceptable because reaching this branch implies the range probe failed anyway and the download will be re-fetched by the single-stream strategy.

## Investigation details

### Investigation A — Integrity exception classification

1. `ResourceIntegrityException extends IOException` is **not** explicitly enumerated in `HttpFailureClassifier.isTransient`. The classifier returns `true` only for `HttpDownloadStatusException` with a transient status, `SocketTimeoutException`, `HttpTimeoutException`, `ConnectException`, `SocketException`, or an `IOException` **whose `getCause()` is one of those network subtypes**. A bare `ResourceIntegrityException` has no nested cause, so it falls through to `return false` → classified permanent. Verified by `exactlyOneTerminalEventWhenIntegrityFailureOccurs`, `segmentedStrategyShouldFailWhenChunkETagChangesAfterProbe`, `...ContentRangeStartMismatch`, `...ContentRangeTotalMismatch`, `...SendsMoreBytesThanRequested`, `...SendsTooFewBytes`, `integrityFailureShouldDeletePartialFile` — all passing.
2. The inheritance from `IOException` does **not** introduce unintended retries. The classifier's `IOException` branch is explicitly guarded on `nested` being a network subtype; `ResourceIntegrityException` has no cause.
3. Wrapping path: `doChunkAttempt` throws `ResourceIntegrityException`; `downloadChunk` rethrows `IOException`/`InterruptedException` unchanged; `RetryExecutor.execute` consults the classifier before wrapping; `SegmentedHttpDownloadStrategy.download` catches the `FailedException` from `StructuredTaskScope` and extracts the cause for `onError`. The cause chain is preserved end-to-end into `DownloadFailedEvent.cause`. Verified by assertions `assertInstanceOf(ResourceIntegrityException.class, failed.cause())` in six separate tests.
4. A single integrity failure cannot be retried against the same invalid representation: `RetryExecutor.execute` at `RetryExecutor.java:71` returns on `!classifier.isTransient(e)` before consulting the policy.
5. Retry exhaustion cannot generate duplicate terminal events because `DownloadFailedEvent` is only emitted by `HttpDownloadSupport.onError`, which is called once per `download(...)` invocation inside the outer `try/catch` — and the integrity path is non-retriable in the first place. Verified by `exactlyOneTerminalEventWhenIntegrityFailureOccurs` (asserts exactly one terminal event with `segmentCount=4` all failing).

**Verdict:** PASS.

### Investigation B — HEAD ↔ Range probe consistency

1. HEAD ETag is passed into `rangeProbe` as the `headETag` parameter (`HttpRangeSupport.rangeProbe`, line 165) and used as the `If-Range` header. The probe response's ETag is extracted and reconciled against `headETag` at lines 202-207; mismatch returns `Optional.empty()` → single-stream fallback. Verified by `rangeProbeReturnsFallbackWhenProbeETagDiffersFromHeadETag`.
2. `headContentLength` (from HEAD) and `Content-Range total` (from the probe) are reconciled at line 187 (`cr.total() != headContentLength → fallback`). The subsequent `ResourceIdentity` uses `headContentLength` as the authoritative size, and every segment response has its Content-Range total compared to it in `validateSegmentResponseHeaders` (line 338).
3. If the representation changes between HEAD and the probe, the probe either sees a different ETag (handled at line 202), a different total size (handled at line 187), or — if the server honors `If-Range` — returns 200 (handled at line 172). In all three cases the orchestrator falls back to single-stream, which is the safe outcome.
4. Weak ETags are rejected at `extractStrongETag` (line 390: `.filter(etag -> etag.startsWith("\""))`). Verified by `probeShouldDiscardWeakETag`. (See RIV-002 for the closing-quote gap.)
5. A probe that gets 200 does not leak resources: `BodyHandlers.ofByteArray` fully consumes the body and `HttpClient` closes/returns the connection. The 200 branch returns `Optional.empty()` before the ETag/Content-Range checks, so no misuse.
6. All probe responses use `BodyHandlers.ofByteArray` (probe) or `BodyHandlers.discarding` (HEAD); neither requires explicit close. The subsequent segment requests use `ofInputStream` and are closed by `try (InputStream inputStream = response.body())` at `SegmentedHttpDownloadStrategy.java:232`.

**Scenarios verified:**

| Scenario | Code path | Outcome | Test evidence |
|---|---|---|---|
| HEAD ETag `"v1"` vs probe ETag `"v2"` | `HttpRangeSupport.java:202-207` | Fallback | `rangeProbeReturnsFallbackWhenProbeETagDiffersFromHeadETag` |
| HEAD advertises ranges; probe returns 200 | `HttpRangeSupport.java:172-175` | Fallback | `rangeProbeReturnsFallbackWhenServerIgnoresRangeAndResponds200`, `orchestratorFallsBackWhenServerRejectsRangeProbWith200` |
| Probe Content-Range inconsistent | `HttpRangeSupport.java:187-190` | Fallback | `rangeProbeReturnsFallbackWhenContentRangeIsAbsent`, Content-Range start/total mismatch cases |
| Probe throws (timeout/IO) | `HttpDownloadOrchestrator.java:131-143` | Catches, logs, returns `Optional.empty()` → fallback | Covered by `headProbe` catch; manually traced |

**Verdict:** PASS.

### Investigation C — Partial FileChannel writes

1. The write loop in `doChunkAttempt` (lines 232-267) does **not** handle short channel writes.
2. `position` advances by `bytesRead` (socket read count), not by the channel's returned write count. See RIV-001.
3. `ByteBuffer.wrap(buffer, 0, bytesRead)` creates a fresh buffer per iteration; cross-iteration state is irrelevant here.
4. The pre-write overflow check (`position + bytesRead > chunk.end() + 1`) ensures the intent-to-write never crosses the boundary, so correctness after a successful full write is maintained. The hazard is only short writes within-bounds.
5. Segment completion is validated against `position - chunk.start()` (line 270), which inherits the same `bytesRead` accounting and would therefore report success even if the channel persisted fewer bytes.
6. An interrupted write in the middle of the buffer could leave the segment under-persisted while the strategy reports success. On local disk `FileChannel` this is empirically very rare but not forbidden by the contract.

**Verdict:** INCONCLUSIVE (correct in the common case; contractually unsafe — see RIV-001).

### Investigation D — Fallback vs. integrity failure separation

1. Unsupported range capability (HEAD has no `Accept-Ranges: bytes`, or size below threshold) → `HttpDownloadOrchestrator.resolveDelegate` lines 87-96 → `HttpDownloadStrategy`. Distinguishable from the "probe succeeded but identity invalid" branch at lines 99-104. Verified by `orchestratorFallsBackToSingleStreamWhenNoETagAvailable`, `orchestratorFallsBackWhenFileSizeBelowSegmentThreshold`.
2. A changed resource identity detected at the probe stage silently becomes a single-stream fallback (lines 202-207 of `HttpRangeSupport`). This is intentional: the segmented strategy never starts, so no partial segments exist to be corrupted. Mid-transfer identity changes cannot be "silently treated as range incompatibility" because segmented chunks always carry `If-Range` and server responses are validated by `validateSegmentResponseHeaders` → `ResourceIntegrityException` (non-retriable). Verified by `segmentedStrategyShouldFailWhenChunkETagChangesAfterProbe`.
3. Fallback after a failed probe is safe: the orchestrator has not yet opened the destination file; only the probe's byte-array body (≤ 1 byte in 206 case) has been materialized.
4. Fallback cannot occur after segmented writes have begun — the orchestrator makes the strategy choice before `SegmentedHttpDownloadStrategy.download` runs; the segmented strategy itself has no fallback path. An integrity failure mid-transfer surfaces as a terminal `DownloadFailedEvent` and the partial file is deleted (`HttpDownloadSupport.deleteFile` at line 150).
5. `StructuredTaskScope.open(Joiner.<Void>awaitAllSuccessfulOrThrow())` ensures that when one chunk throws, the scope cancels sibling forks and surfaces `FailedException`. Concurrent workers cannot keep writing after an integrity failure. Verified by `exactlyOneTerminalEventWhenIntegrityFailureOccurs` which uses 4 segments and still observes exactly one terminal event.
6. Terminal events are emitted exactly once: the segmented `download` method has three outer `catch` branches (`FailedException`, `DownloadCancelledException`, `Exception`), each calls exactly one of `onComplete`/`onCancelled`/`onError`. The explicit test `exactlyOneTerminalEventWhenIntegrityFailureOccurs` asserts count == 1.
7. Diagnostic causes are preserved: `FailedException.getCause()` is unwrapped and passed to `onError` (line 153-154), which stores it in `DownloadFailedEvent.cause`.

**Verdict:** PASS.

## Cross-cutting concerns

- **Progress accounting.** `totalDownloaded` can only exceed `contentLength` if the overflow guard at line 240 is bypassed; the guard rejects any read that would cross the per-chunk boundary before `channel.write` or `totalDownloaded.addAndGet` is called. On retry, `attemptBytes` is subtracted from `totalDownloaded` in the catch blocks (lines 277, 287). Progress rewind is correct for all non-cancellation failure paths. Cancellation correctly skips rewind so the cancelled event carries the last observed total.
- **InactivityWatchdog interaction.** Integrity failures throw synchronously from `validateSegmentResponseHeaders` or the overflow guard; the watchdog's `finally` block (line 290) closes it in all paths. No interaction hazard.
- **Pause/resume.** `pausedFired` / `resumedFired` `AtomicBoolean`s ensure exactly one `DownloadPausedEvent` / `DownloadResumedEvent` across N concurrent chunk threads (lines 314-336). No regression observed.
- **FileChannel cleanup.** The `try (FileChannel channel = ...)` at line 125 guarantees close even when the structured scope throws `FailedException`.

## Recommendation

**ACCEPT WITH FOLLOW-UPS.**

Rationale: All acceptance criteria are demonstrated by passing tests, and the integrity guarantees (non-retry, single terminal event, partial-file cleanup, ETag/If-Range enforcement, overflow/truncation detection, safe HEAD↔probe reconciliation) are correctly implemented end-to-end. The two identified issues are:

- **RIV-001 (partial FileChannel write)** — a real contract violation but one that, on the local-disk FileChannels used by the current implementation, almost never produces a short write. It does not invalidate any T07 acceptance claim demonstrated by the existing tests and does not block proceeding to T08.
- **RIV-002 (ETag closing-quote check)** — a minor hardening item with no test currently reaching the edge case.

Neither finding is a confirmed blocking defect. Both should be tracked as follow-up items and addressed before T07's guarantees are relied on in production, but they do not require a correction cycle before T08 begins.

If a stricter stance is preferred, the single minimum blocking correction would be RIV-001 only: convert the single `channel.write` call into a drain loop and drive progress/validation from bytes actually written.
