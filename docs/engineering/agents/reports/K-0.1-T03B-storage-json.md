# K-0.1-T03B — Versioned JSON Codec & Storage Abstraction — Report

## Status

Complete

## Objective

Design and implement a version-aware JSON codec with schema migration, isolated in a new Maven/JPMS module. No file storage, checkpoint scheduling, or DownloadManager integration.

## Module Decision

**New module introduced: `katabasis-storage-json`** (`jsanca.katabasis.storage.json`)

Rationale in [ADR-009](../../adr/ADR-009-storage-json-module.md). Summary: the codec has a different dependency set (Jakarta JSON-B/JSON-P) that the HTTP download engine has no use for; independent testability and downstream consumer independence both justify the module. A further split into `katabasis-storage-api` was deferred (single implementation, YAGNI).

## Architecture

### Envelope format

```json
{
  "envelopeVersion": "1",
  "type": "download-task",
  "id":   "task-abc",
  "schemaVersion": 2,
  "revision": 7,
  "payload": { ... }
}
```

`envelopeVersion` is an opaque string that guards the outer structure. `schemaVersion` is a positive integer governing the payload schema. `revision` is a non-negative monotonic counter for optimistic concurrency (zero = new document).

### API surface (`jsanca.katabasis.storage.json.api`)

| Type | Description |
| --- | --- |
| `StorageKey` | Stable logical identity — `type` + `id`, validated against `[a-zA-Z0-9][a-zA-Z0-9_-]*` |
| `VersionedCodec<T>` | encode/decode interface; no JSON framework types |
| `StorageDocument<T>` | Decoded envelope metadata + payload |
| `CodecException` | Unchecked; thrown for structural, schema, or migration errors |

### Internal structure

| Package | Contents |
| --- | --- |
| `internal.codec` | `JsonEnvelopeCodec<T>` — builder pattern, Jsonb + JSON-P envelope |
| `internal.migration` | `Migration` interface (pure function, `fromVersion()` → `fromVersion()+1`), `MigrationRegistry` (chain validation + ordered application) |
| `internal.adapter` | `UriAdapter`, `PathAdapter` — register in codec builder as needed |

### Schema resource

`META-INF/schemas/envelope-v1.schema.json` — JSON Schema Draft 2020-12 documenting the envelope contract. Programmatic validation is used at runtime (not a full JSON Schema library); see ADR-009 for the deferral reasoning.

### Migration mechanism

`MigrationRegistry` validates the migration chain at construction (no gaps, no duplicates). `JsonEnvelopeCodec.decodeDocument` extracts the stored `schemaVersion`, passes the raw payload to `MigrationRegistry.migrate(payload, storedVersion, currentVersion)`, then deserializes the migrated JSON with JSON-B. Documents with `storedVersion > currentSchemaVersion` throw `CodecException` (do not silently downgrade). No arbitrary class loading from document metadata.

## Limitations and Open Items

- **JSON Schema runtime validation deferred.** The envelope schema is enforced programmatically. A full JSON Schema validator (Draft 2020-12) requires a JPMS-compatible library — `networknt/json-schema-validator` uses an automatic module name and was not adopted. Document the gap; revisit when payload schemas per entity type are defined.
- **`DownloadStateStore` integration not implemented.** `katabasis-core`'s `DownloadStateStore` interface remains a placeholder. Wiring it to `JsonEnvelopeCodec` is K-0.2 scope.
- **Deterministic byte output.** JSON-B does not guarantee field ordering. The byte representation of `encode()` is not content-stable across JVM versions. If content hashing is needed, hash the round-tripped domain object, not the raw bytes.
