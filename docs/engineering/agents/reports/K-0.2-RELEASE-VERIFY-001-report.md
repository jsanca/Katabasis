## 3. CheckpointCoordinator Discrepancy Resolution

**Finding:** The K-0.2-T10-HARDEN-001 report (Change 2) described a guard in `flushPending()`:
> "Added guard: when `sourceProvider.findSource()` returns empty and the pending snapshot's status is non-terminal, skip save and remove the stale entry from `pending`."

**Current code** (`CheckpointCoordinator.flushPending()`):

```java
private void flushPending() {
    pending.forEach((id, snap) ->
            pending.computeIfPresent(id, (k, existing) -> {
                final Optional<CheckpointSource> srcOpt = sourceProvider.findSource(k);
                final DownloadSnapshot toSave = srcOpt.isPresent()
                        ? srcOpt.get().buildSnapshot(Instant.now())
                        : existing;  // falls back to event-derived snapshot
                saveWithObservability(toSave);
                return toSave;
            }));
}
```

The guard is **not present**. This is a documentation inaccuracy in the report, not a code defect.

**Analysis of correctness without the guard:**

The overwrite risk the guard would protect against is: `coordinator.close()` calling `flushPending()` with stale event-derived data for a download whose authoritative snapshot was already written by `notifyShutdownCheckpoint`. This cannot happen because:

1. `manager.close()` runs before `coordinator.close()` (enforced in CLI and UI).
2. During `manager.close()`'s post-quiescence loop, `notifyShutdownCheckpoint` calls `pending.remove(id)` before saving. Any subsequent `flushPending()` call finds no entry for that ID.
3. The race where a periodic flush saves stale data between manager quiescence and `notifyShutdownCheckpoint` is handled by the "authoritative snapshot saves last" guarantee: `notifyShutdownCheckpoint` removes from pending, then saves; a concurrent flush either (a) finds the entry gone (no-op) or (b) saves the stale entry first, which `notifyShutdownCheckpoint`'s subsequent save overwrites.
4. The `naturallyTerminatedDuringShutdown` filter in `DefaultDownloadManager.close()` ensures completed/failed downloads are skipped by the post-quiescence loop, so their pending entries (already removed by `handleCompleted`/`handleFailed`) are not touched.

**Verdict:** MEDIUM documentation issue. The code is correct. The report described a planned guard that was superseded by the `notifyShutdownCheckpoint` design. No code change required.
