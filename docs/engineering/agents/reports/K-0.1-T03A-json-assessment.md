# K-0.1-T03A — JSON Dependency & Compatibility Assessment — Report

## Status

Complete

## Objective

Determine the JSON technology already available in Katabasis and select the smallest reliable solution for versioned JSON serialization of download snapshot structures. No persistence or versioning implementation — spike only.

## Findings

### 1. Dependency tree — no JSON library present

`katabasis-core` has three runtime dependencies: `commons-lang3:3.20.0`, `slf4j-api:2.0.12`, `slf4j-simple:2.0.12`. Jackson is absent. No JSON library of any kind exists in the project.

### 2. JPMS module-info baseline

`module-info.java` requires: `org.apache.commons.lang3`, `java.net.http`, `org.slf4j`. No JSON-related reads.

### 3. Jackson — not evaluated

Jackson is absent from the dependency tree. It was not evaluated. Adding Jackson would introduce a large transitive closure and annotation-driven magic contrary to the project's coding conventions.

### 4. Jakarta JSON-B 3.0 + Eclipse Yasson 3.0.5 — selected

Evaluated artifacts (all present in local Maven repo under correct coordinates):

| Artifact | Coordinates | JPMS module name | Module type |
| --- | --- | --- | --- |
| Jakarta JSON-B API 3.0.1 | `jakarta.json.bind:jakarta.json.bind-api:3.0.1` | `jakarta.json.bind` | Named (module-info.class) |
| Jakarta JSON-P API 2.1.3 | `jakarta.json:jakarta.json-api:2.1.3` | `jakarta.json` | Named (module-info.class) |
| Eclipse Yasson 3.0.5 | `org.eclipse.yasson:yasson:3.0.5` | `org.eclipse.yasson` | Named (module-info.class) |
| Eclipse Parsson 1.1.7 | `org.eclipse.parsson:parsson:1.1.7` | `org.eclipse.parsson` | Named (module-info.class) |

All four have proper `module-info.class` — no automatic module name fragility.

Previously tested coordinates `org.glassfish:parsson` and `org.eclipse.yasson:yasson:3.0.4` are incorrect or absent from Central; the correct group for both is `org.eclipse.*`.

Yasson's `module-info` requires: `jakarta.json.bind`, `jakarta.json`, `jakarta.cdi static` (CDI is optional), `java.logging`. The `static` requires are optional and do not need to be satisfied. Parsson provides `jakarta.json.spi.JsonProvider` via ServiceLoader, discovered automatically at runtime.

### 5. Compatibility verified

Round-trip test `JsonbCompatibilityTest` covers:

| Scenario | Result |
| --- | --- |
| Java 25 public record with primitives, `URI`, `Path`, `Instant` | Pass |
| Nullable `String` field (null → absent in JSON → null after restore) | Pass |
| Nested record (`SourceInfo` inside `TaskSnapshot`) | Pass |
| `List.of()` immutable collection (round-tripped as mutable `ArrayList`, contents equal) | Pass |
| All five `TaskStatus` enum values | Pass |

**URI / Path** require custom `JsonbAdapter` implementations — they are not natively serializable. `Instant` is handled natively by JSON-B 3.0 (ISO-8601 string).

**JPMS compatibility note**: Maven Surefire 3.5.3 with this project runs tests in classpath mode (not module-path mode), confirmed by "Unknown module: jsanca.katabasis.core" warnings. The `--add-reads` flags added to the testCompile execution are correct for a future strict module-path setup; they produce only warnings (not errors) in classpath mode. The `public` visibility requirement on record types is a real Yasson constraint — test records must be `public` (or the enclosing class must be `public`) for Yasson to invoke their accessors via `MethodHandles`.

### 6. JPMS boundary — domain APIs are clean

`JsonbCompatibilityTest` confines all JSON-B types to the test class. No `jakarta.json.bind.*` types appear in any `api.*` package. The `DownloadTaskSnapshot` record (when implemented) will carry only standard Java types; the `JsonbAdapter` for `URI` and `Path` will live in `internal.json`.

## Decision

**Selected: Jakarta JSON-B 3.0 + Eclipse Yasson 3.0.5 + Eclipse Parsson 1.1.7**

Rationale:
- Zero annotation magic — JSON-B maps records by convention (public accessors + canonical constructor)
- Full JPMS module-info on all artifacts
- Minimal footprint (4 jars, no transitive surprises)
- JSON-B 3.0 ships with native `Instant` support; `URI`/`Path` require one adapter each
- Consistent with Jakarta EE ecosystem already implied by Java 25 target

## Implementation Notes for K-0.1-T03B (future)

When `DownloadTaskSnapshot` is implemented:
- Record fields must be standard Java types (`URI`, `Path`, `Instant`, primitives, `String`, `List`, `Optional` mapped to nullable)
- Register `UriAdapter` and `PathAdapter` in the `JsonbConfig` at the persistence boundary
- Keep `JsonbConfig` construction inside `internal.json`; never expose `Jsonb` or `JsonbConfig` through `api.*`
- `Optional` fields: map to nullable `String`/`long` etc. in the snapshot record; the adapter layer handles the mapping
