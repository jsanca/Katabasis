# K-0.2-T10 — Storage Wiring & Consistent Checkpoints

## Status

Complete

## Objective

Wire persistent checkpoints into the active download execution path so that a real HTTP download
produces a versioned JSON manifest containing trustworthy recovery metadata: segment boundaries,
ETag, and confirmed bytes at the moment of snapshot.

## Design Summary

### SPI: CheckpointSource (Option B)

`CheckpointSource` is a core-owned `@FunctionalInterface` that strategies register on `DownloadTask`:

```java
@FunctionalInterface
public interface CheckpointSource {
    DownloadSnapshot buildSnapshot(Instant at);
}
```

This keeps the interface boundary clean: core owns the port; storage-json calls through it.

### CheckpointSourceProvider

A separate lookup interface (`Optional<CheckpointSource> findSource(String downloadId)`)
implemented by `DefaultDownloadManager`. Callers cast the returned `DownloadManager` to
`CheckpointSourceProvider`; the cast always succeeds because `createDefault(...)` always
returns `DefaultDownloadManager`.

### Per-segment confirmed bytes

`SegmentedHttpDownloadStrategy` now maintains `AtomicLong[] segmentConfirmedBytes`
(one entry per chunk), mirroring the rewind semantics of `totalDownloaded` on `IOException`.
The checkpoint aggregate is `sum(segmentConfirmedBytes[i])` — it cannot exceed the actual
bytes written to disk even under concurrent retries.

### Shutdown ordering

`DownloadManagers.createDefault(config, shutdownSnapshotConsumer)` accepts a
`Consumer<DownloadSnapshot>` that is called per active task **before** signalling cancellation
in `close()`. This ensures the final pre-cancel state reaches the store before the executor
drains. Cancelled events for shutdown-initiated cancellations are suppressed so the coordinator
does not delete the saved snapshot.

### Observable persistence failures

`saveWithObservability()` and `deleteWithObservability()` emit `DownloadCheckpointFailedEvent`
to the supplied `failureConsumer` rather than swallowing exceptions silently.

## Checkpoint Directory

Both CLI commands and the UI application resolve checkpoints to
`~/.katabasis/checkpoints`, created on first use. Interval is 5 seconds.

## Architectural Notes

- `DefaultDownloadManager` simultaneously implements `DownloadManager` (public) and
  `CheckpointSourceProvider` (semi-public), with the latter hidden behind an explicit cast.
  This avoids widening the `DownloadManager` interface with checkpoint concerns.
- Backward compatibility: `CheckpointCoordinator.create(manager, store, interval)` is
  retained, delegating to a no-op source provider and no-op failure consumer.
- `partialPath = null` in all snapshots: both strategies write directly to `targetPath`.
  Recovery logic (K-0.2-T11) will need to account for this.

## Handoff to K-0.2-T11

Snapshots now contain accurate `confirmedBytes`, `segments` (for segmented downloads), and
`etag`. Recovery can use these to resume from byte offset after a process restart — the
implementation is deferred to K-0.2-T11.
