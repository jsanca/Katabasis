# K-0.2-T09 — ADR-002 Persistence Strategy Report

## Status

Complete

## Objective

Produce ADR-002 to formally record the versioned JSON persistence strategy for Katabasis 0.2,
assess the implementation against that strategy, reconcile prior storage review findings, and
deliver an actionable handoff to T10 and T11.

## Assessment Summary

The existing `katabasis-storage-json` implementation is structurally sound and consistent with
the versioned JSON strategy. No architectural contradictions were found. ADR-002 was created
with status **Accepted** directly (not Proposed) because the decision was already established
through K-STOR-HARDEN-001 and K-STORAGE-REVIEW-001; this ADR formalizes it.

## Architecture Assessment

The module boundary is clean: `katabasis-core` owns the `DownloadStateStore` port and domain
records; `katabasis-storage-json` owns all JSON and filesystem implementation details. No
JSON-B or filesystem types cross the port boundary. The dependency direction (storage → core)
is unidirectional and correct.

The `CheckpointCoordinator` integrates with `DownloadManager` as an event listener, which is
the right pattern for loose coupling. Its current limitation (building snapshots from public
events only) is a known and documented gap, not an architectural flaw.

## Prior Finding Reconciliation

All 15 findings from K-STORAGE-REVIEW-001 were reviewed against the current code:

- **8 resolved** (STOR-001, 002, 003, 005, 007, 008, 012, 013) — confirmed in current
  `FileDownloadStateStore.java` and `CheckpointCoordinator.java`.
- **4 accepted limitations** (STOR-006, STOR-009, STOR-010, STOR-011) — documented in ADR-002
  with explicit phase-0.2 applicability.
- **2 deferred** (STOR-014, STOR-015) — low-priority design improvements; no blocking issue.
- **1 superseded** (STOR-004) — ADR-009 amendment; now covered by ADR-002 directly.

None of the deferred or accepted findings block T10 wiring. STOR-010 (corrupt manifest
quarantine) is desirable before T11 ships to users but not blocking for a first implementation.

## T10 Wiring Gap Analysis

The current `CheckpointCoordinator` produces snapshots with:
- Populated: `downloadId`, `sourceUri`, `targetPath`, `confirmedBytes`, `expectedTotalBytes`,
  `status`, `createdAt`, `checkpointAt`
- Always null/empty: `partialPath`, `etag`, `segments`

These three fields carry internal execution state unavailable via public events. T10 must
resolve this. The recommended approach (documented in ADR-002) is enriching `DownloadStartedEvent`
and `DownloadProgressEvent` with `partialPath`, `etag`, and `List<SegmentSnapshot>` so the
coordinator remains event-driven without coupling to internal classes.

## T11 Recovery Prerequisites

T10 must produce snapshots with populated `etag` and `segments` before T11 recovery is
meaningful for segmented downloads. T11 recovery validation sequence is documented in ADR-002
(§ T11 Handoff).

evolution without code changes.
