# K-0.1-T03D — Retry Policy & Execution Engine — Report

## Status

Complete

## Summary

Implemented a protocol-agnostic retry mechanism and integrated it with the HTTP download strategies. 150 tests pass (87 katabasis-core, 63 katabasis-storage-json).

## Design

### Separation of concerns

| Concern | Type | Location |
| --- | --- | --- |
| Configuration data | `RetryConfig` (api/model) | Public API — carries kind, maxAttempts, delays, jitter |
| Retry timing algorithm | `RetryPolicy` interface + 3 implementations | `internal.retry` |
| Failure classification | `FailureClassifier` interface | `internal.retry` |
| HTTP-specific classification | `HttpFailureClassifier` | `internal.http` |
| Retry loop execution | `RetryExecutor` | `internal.retry` |
| Factory | `RetryPolicies` | `internal.retry` |

### Key invariants

- `DownloadCancelledException` is **never** retried — `RetryExecutor` re-throws it immediately.
- Cancellation flag checked **before** sleeping — no sleeping if already cancelled.
- Non-transient failures (`FailureClassifier.isTransient == false`) are not retried regardless of policy.
- Only terminal failures (after retry exhaustion or permanent classification) emit `DownloadFailedEvent`.

### HTTP failure classification

| Category | Examples | Transient? |
| --- | --- | --- |
| Network | `ConnectException`, `SocketTimeoutException`, `HttpTimeoutException`, `SocketException` | Yes |
| HTTP 429 | Too Many Requests | Yes |
| HTTP 5xx (except 501) | 500, 502, 503, 504 | Yes |
| HTTP 501 | Not Implemented | No |
| HTTP 4xx | 400, 401, 403, 404 | No |
| Generic IOException | Disk errors, etc. | No |

### Exponential backoff formula

```
baseMs = min(initialDelay * 2^failedAttempts, maxDelay)
jitter = baseMs * jitterFactor * random.nextDouble()   (0 if jitterFactor == 0)
delay  = min(baseMs + jitter, maxDelay)
```

Left-shift is capped at 62 bits to prevent long overflow.

## Per-request override wiring

```
DownloadRequest.retryConfig() → Optional<RetryConfig>
  ↓ orElse
DownloadConfig.retryConfig()   (global default)
  ↓
DownloadManagers passes effectiveRetry to DownloadExecutionContext
  ↓
DownloadExecutionContext.retryExecutorFor(HttpFailureClassifier.INSTANCE)
  ↓
HttpDownloadStrategy / SegmentedHttpDownloadStrategy wraps attempt in RetryExecutor.execute()
```

## Open Items

- Jitter uses `new Random()` (not `ThreadLocalRandom`) in `RetryPolicies.fromConfig(RetryConfig)` for testability. Production callers that want better concurrent performance may pass `ThreadLocalRandom.current()` via the two-arg overload.
- `RetryExecutor` holds the retry permit for the full download duration including sleep intervals. The semaphore in `DownloadExecutors` is therefore held during delays — documented and acceptable for 0.1; K-0.2 may address this.
