# K-0.2-T10-HARDEN-001 — Coordinated Graceful Shutdown & Final Checkpoint

## Status

Complete

## Objective

Fix the shutdown-ordering race: CLI and UI were calling `coordinator.close()` before
`manager.close()`, so the coordinator's final flush ran while workers were still active.
Move the authoritative snapshot to after worker quiescence and prevent the coordinator's
post-close flush from overwriting that authoritative snapshot.

---

## Section 4 — Architecture Diagnostic

### Q1: When does a worker stop writing bytes?

After `task.requestCancellation()` is cooperatively observed in the copy loop of
`SegmentedHttpDownloadStrategy`. The cancellation token is polled on each iteration; when
observed, the loop exits without further writes. The worker emits `DownloadCancelledEvent`
(suppressed by `shutdownCancelledIds`), returns from `strategy.download()`, and the finally
block of `runDownload()` removes the task from the registry.

### Q2: When is its final confirmed offset published?

`AtomicLong[] segmentConfirmedBytes` are updated on each successful write. The final
values are whatever was written before the cancellation token was polled. The aggregate
sum computed by `checkpointSource.buildSnapshot()` at that moment is a strict under-estimate
if cancellation interrupted mid-write, but monotonically increasing and consistent.

### Q3: When is its CheckpointSource removed?

Never cleared. The `volatile checkpointSource` field on `DownloadTask` is set once when
the HTTP strategy registers it and never nulled. It becomes inaccessible via
`findSource()` only after `downloadRegistry.remove()` in `runDownload()`'s finally block,
but the task object remains alive while any reference is held (e.g., from a captured list).

### Q4: Can manager shutdown suppress events required by checkpointing?

Yes. `shutdownCancelledIds` suppresses `DownloadCancelledEvent` for shutdown-initiated
cancellations. The coordinator never sees the terminal event and therefore does not delete
the manifest — intentional for recovery.

### Q5: Can coordinator closure race with an active flush?

Before this fix: yes, in two ways. First, the scheduled flush and `close()`'s `flushPending()`
could both run; `flushTask.cancel(false)` does not interrupt an in-progress flush and
`awaitTermination(30s)` serialises them. Second and more importantly, the coordinator was
closed while workers were still running, so `flushPending()` saved an in-flight snapshot
rather than a quiescent one.

After this fix (manager closed first): no active workers exist when `coordinator.close()`
runs. `flushPending()` guard (see Change 2) prevents stale overwrite.

### Q6: Does manager.close() returning imply actual quiescence?

Yes, on the happy path. `executor.close()` calls `awaitTermination(10 s)`. When it returns
without timeout, all virtual threads have completed `runDownload()` including registry removal.

### Q7: What happens if the termination timeout expires?

The executor logs a warning and returns; `manager.close()` continues. Workers may still be
writing bytes. The post-quiescence snapshot logic executes anyway — snapshots are best-effort
but potentially inconsistent. No observable signal is emitted. This is a known gap documented
here; a separate sub-task is needed to surface timeout as `DownloadCheckpointFailedEvent`.

### Overwrite race identified

If `coordinator.close()` runs after `manager.close()`, its `flushPending()` calls
`sourceProvider.findSource(k)` which returns `Optional.empty()` (task deregistered),
falls back to the stale event-derived pending snapshot, and saves it — overwriting the
authoritative post-quiescence snapshot. Fix: skip save in `flushPending()` when source is
absent and status is non-terminal.

## Changes

### 1. `DownloadManagers.java` — `DefaultDownloadManager.close()`

**Before:** snapshot built inside write lock, while workers alive, before cancellation.

**After:** task references captured inside write lock; cancellation requested; write lock
released; `executor.close()` drains workers; snapshot built from captured sources **after
quiescence**; consumer called in finally to guarantee execution even if executor close throws.

Javadoc on `createDefault(config, consumer)` updated to reflect the new post-quiescence
contract.

### 2. `CheckpointCoordinator.java` — `flushPending()`

Added guard: when `sourceProvider.findSource()` returns empty **and** the pending
snapshot's status is non-terminal, skip save and remove the stale entry from `pending`.
Rationale: absence of source with non-terminal status means the manager already persisted
an authoritative post-quiescence snapshot; saving the stale event-derived entry would
overwrite it.

### 4. `DownloadManagers.java` — naturally-terminated task filter

Added `naturallyTerminatedDuringShutdown` set (populated in `emit()` for `DownloadCompletedEvent`
unconditionally, and for `DownloadFailedEvent` when not in `shutdownCancelledIds`). The
post-quiescence loop skips IDs in this set, preventing a spurious `notifyShutdownCheckpoint`
call for downloads that completed or failed before or during the executor drain window.

### 5. `CheckpointCoordinator.java` — `notifyShutdownCheckpoint()`

New method: atomically removes the ID from `pending` (preventing stale overwrite on
`close()`) and immediately saves the authoritative post-quiescence snapshot to the store.
Called by the manager's shutdown consumer for each shutdown-cancelled active download.

### 6. `CheckpointCoordinatorTest.java` — 4 new unit tests for `notifyShutdownCheckpoint`

- `notifyShutdownCheckpointSavesSnapshotToStore` — snapshot is persisted
- `notifyShutdownCheckpointRemovesFromPendingBeforeSave` — pending entry removed; close() does not overwrite
- `notifyShutdownCheckpointNullSnapThrows` — null guard
- `notifyShutdownCheckpointWithSourceProviderPreventsFlushOverwrite` — provider path: close() does not re-query source for the already-handled ID

### 3. `DownloadCommand.java`, `DownloadListCommand.java`, `DownloadManagerApplication.java`

Swapped close order: `manager.close()` first, then `coordinator.close()`. Manager now
handles the final authoritative snapshot internally; coordinator's close is now purely
scheduler teardown + flush of any surviving entries.

## Known Gaps

- **Timeout observability (Q7):** `VirtualThreadDownloadExecutor` logs a warning but returns
  `void`; `manager.close()` has no mechanism to emit a `DownloadCheckpointFailedEvent` on
  timeout. Deferred to a follow-up sub-task.
- **Single-segment HTTP strategy:** `HttpDownloadStrategy` does not register a
  `CheckpointSource`; its downloads produce `checkpointSource() == null` on the task. The
  shutdown snapshot loop skips these (null guard). No regression — same behavior as before.
