## 1. Objective

Verify the complete HTTP download lifecycle through the Katabasis public `DownloadManager` API
using a deterministic in-process HTTP server. Prove component interaction, not just isolation.

---

## 2. Assessment: Existing Coverage Before T09

A survey of all existing tests found the following gaps against the T09 scenario categories:

| Gap | Existing level | Root cause |
|---|---|---|
| Segmented success (B) | Strategy/orchestrator only | No test drove a segmented download through `DownloadManagers.createDefault()` |
| Retry success + exhaustion (D, E) | Strategy direct | All retry tests bypassed the public API |
| HTTP timeout (F) | Unit (`InactivityWatchdogTest`) | No integration test connecting stalled server → watchdog → event |
| Segmented cancellation (H) | Strategy direct | Public API not exercised |
| Segmented pause/resume (I) | Strategy/ctx direct | Public API not exercised |
| Terminal event uniqueness (J) | Strategy/orchestrator | Not exercised via public API |

Single-stream success, single-stream cancel, and single-stream pause/resume were already covered
by `DownloadManagerTest` via the public API and were not duplicated.

## 3. New Tests — `DownloadManagerE2ETest`

9 new integration tests in `jsanca.katabasis.core.api.manager.DownloadManagerE2ETest`.
Every test drives the download through `DownloadManagers.createDefault(DownloadConfig)`.

### In-process server

A single `TestHttpServer` class handles:
- **HEAD** — Content-Length, optional Accept-Ranges + ETag
- **Range probe bytes=0-0** — 206 with Content-Range + ETag (when configured)
- **Chunk GET** — 206 with correct Content-Range and optional throttle
- **Full GET** — 200 with optional throttle or body stall after first byte
- **Scripted failures** — first N non-HEAD requests return a configured error code

The server shuts down and closes its `ServerSocket` on `close()` after every test.

### Test methods and scenario coverage

| Test | T09 Scenario |
|---|---|
| `downloadManagerShouldCompleteSegmentedDownload` | B: segmented success |
| `downloadManagerShouldFallBackToSingleStreamWhenContentBelowSegmentThreshold` | C: range fallback (size) |
| `downloadManagerShouldUseSingleStreamWhenServerDoesNotAdvertiseRanges` | C: range fallback (no header) |
| `downloadManagerShouldRetryAndCompleteAfterTransientFailure` | D: transient failure + retry |
| `downloadManagerShouldEmitExactlyOneFailedEventAfterRetryExhaustion` | E: retry exhaustion |
| `downloadManagerShouldFailWhenBodyStallsAndReadInactivityTimeoutExpires` | F: HTTP timeout |
| `downloadManagerShouldCancelSegmentedDownloadAndEmitCancelledEvent` | H: segmented cancel |
| `downloadManagerShouldPauseAndResumeSegmentedDownloadToCompletion` | I: segmented pause/resume |
| `downloadManagerShouldEmitExactlyOneTerminalEventOnSegmentedIntegrityFailure` | G+J: identity change + uniqueness |

## 4. Notable Findings During Test Development

No production defects were uncovered. All scenarios behaved as designed:

- `ReadInactivityTimeoutException extends HttpTimeoutException` → classified transient → retried
  when retry is configured; propagated as `DownloadFailedEvent` with `RetryConfig.noRetry()`.
- Per-request `retryConfig` in `DownloadRequest` correctly overrides the global `DownloadConfig`
  default (`RetryConfig.noRetry()`) — verified by the retry success and exhaustion tests.
- `DownloadConfig.httpTimeoutConfig` propagates correctly through
  `DefaultDownloadStrategyResolver` → `HttpDownloadOrchestrator` → `HttpDownloadStrategy`.
- Segmented partial-file deletion on cancellation is observable via `assertFalse(Files.exists(dest))`.

---

## 5. Remaining Coverage Limitations

- **Scenario G (resource identity change) via DownloadManager**: tested at strategy level in
  `ResourceIntegrityTest` (ETag change, Content-Range mismatch, overflow, truncation). No
  DownloadManager-level test — an inline server would need to serve different ETags per request
  phase, which is equivalent to the strategy test with no additional stack coverage.
- **Response timeout via DownloadManager**: not integration-tested because simulating stalled
  headers requires blocking the accept loop, which risks flakiness. Unit semantics: the timeout
  is passed to `HttpRequest.timeout()`.
- **Segmented transient failure via DownloadManager**: covered at strategy level in
  `HttpLifecycleTest.segmentedRetrySucceedsAfterTransientChunkFailure`. Not duplicated via
  DownloadManager — adds no new coverage since the retry path is identical.
