### Reconciliation: "DownloadStateStore is a placeholder"

`AGENTS-CORE.md` states: *"The `DownloadStateStore` interface is a placeholder for future persistence."* This is **stale**. The `DownloadStateStore` interface is fully specified, `FileDownloadStateStore` implements it completely, and `katabasis-storage-json` is a production-ready persistence module tested by 63 passing tests. The description was accurate prior to K-0.1-T03B/C but was never updated. `AGENTS-CORE.md` requires a targeted correction.

What is **not yet present** is integration: `DownloadManagers.createDefault()` accepts no `DownloadStateStore`, does not create a `CheckpointCoordinator`, and emits no snapshots with ETag or segment data. The gap is wiring and data flow, not implementation of the store itself.

No completed 0.1 tasks need to be reopened. The placeholder scheduling components are forward-reserved for a future queuing/prioritisation feature not on the 0.2 roadmap.

## 3. ADR-003 — DownloadManager Lifecycle Recommendation

### Current state

`DownloadManager` has no shutdown API. `DefaultDownloadManager` holds a `Executors.newVirtualThreadPerTaskExecutor()` instance that is never shut down. `CheckpointCoordinator` is `AutoCloseable` and handles its own cleanup correctly, but it is not wired into the manager. There is no way for a caller to drain or terminate in-flight downloads.

### Recommendation

**Add `AutoCloseable` to `DownloadManager`.**

#### `close()` semantics

1. **Reject new submissions.** Once `close()` is called, `download()` throws `IllegalStateException`. Callers that check the return value of `download()` before using the ID are unaffected; callers that submit concurrently with shutdown receive a clear error.
2. **Cancel all active and paused downloads.** Issue a cancellation token to every task currently in `DownloadRegistry`. Paused downloads must be cancelled explicitly — they hold a semaphore permit indefinitely and would block executor shutdown.
3. **Await termination with a bounded timeout.** Call `executor.shutdown()` then `executor.awaitTermination(shutdownTimeout, SECONDS)`. A reasonable default is 10 seconds (configurable via `DownloadConfig`). If the timeout expires, log a warning and proceed; do not block indefinitely.
4. **Flush checkpoints last.** The `CheckpointCoordinator` (if wired) must have its `close()` called after the executor shutdown completes, so that all terminal events have been processed before the final flush writes them to disk.

#### Treatment of active and paused downloads

| State at `close()` | Action |
|--------------------|--------|
| Active (in-flight) | Cancel immediately; wait for cooperative exit up to `shutdownTimeout` |
| Paused | Cancel; the `PauseCoordinator.clear` path in `runDownload`'s `finally` block handles cleanup |
| Queued (waiting for semaphore) | Interrupted on executor shutdown; the `InterruptedException` path in the executor's lambda is already handled |

#### Relationship to durable checkpoints

`close()` must NOT call `store.delete()` for cancelled-on-shutdown downloads. Those downloads may be recoverable after restart — their status at the time of checkpoint should remain `IN_PROGRESS` or `PAUSED`, not `CANCELLED`. The checkpoint coordinator's behaviour of deleting on `DownloadCancelledEvent` is correct for user-initiated cancels but becomes a problem for shutdown-initiated cancels. This requires either:
- A flag distinguishing user-cancel from shutdown-cancel, or
- A separate `DownloadManager.shutdown()` method that marks the event as non-terminal for persistence purposes

**Recommended approach:** a separate `shutdown()` on `DownloadManager` (complementing `cancel(id)`) that fires a `DownloadSuspendedEvent` instead of `DownloadCancelledEvent`. The coordinator retains the snapshot. This is a small addition but preserves recovery semantics. If `DownloadManager` already implements `AutoCloseable`, `close()` delegates to `shutdown()`.

#### Resource ownership

`DownloadExecutors.createVirtualThreadExecutor` creates the `ExecutorService`; `DownloadManagers.createDefault` creates the manager. The manager must own the executor and shut it down in `close()`. The `CheckpointCoordinator` is currently created and owned by the caller; this is acceptable for now. A future factory overload (`DownloadManagers.createWithStorage(config, store)`) can create and own both.

## 4. ADR-004 — CLI Framework Recommendation

### Candidates evaluated

| Criterion | picocli | Hand-rolled |
|-----------|---------|-------------|
| Java 25 / JPMS | Full support — `info.picocli` module, `module-info.java` provided by upstream | No issue — pure Java |
| Maven | Single dependency (~700 KB), no annotation processor required at runtime | Zero deps |
| Subcommands | First-class: annotated `@Command` hierarchy, automatic routing | Manual dispatch map |
| Argument parsing & validation | Type converters, mandatory/optional, default values, enum mapping | Manual `String` parsing |
| Help text | Auto-generated `-h`/`--help`, usage synopsis, description | Hand-written, maintenance burden |
| Exit codes | `CommandLine.execute()` returns int; `@ExitCode` mapping for exceptions | `System.exit()` calls |
| Progress output | Orthogonal (output to stderr while return value goes to stdout) | Same |
| Testability | `CommandLine.execute(args)` in unit tests; no process spawn required | Same |
| Native image | GraalVM native image support with `@picocli.codegen.aot.graalvm.ReflectionConfigGenerator` | No issue |

### Recommendation: **picocli**

The 0.2 CLI requires at least 5 subcommands (download, list, cancel, pause, resume), typed arguments (URL, Path, int), and standardized exit codes. Hand-rolling this is feasible but produces 300–400 lines of parsing boilerplate that offers no reuse value. picocli eliminates that boilerplate while remaining fully JPMS-compatible.

**Trade-off accepted:** one new runtime dependency on `info.picocli`. This requires an `--add-opens` or `requires info.picocli` declaration in `katabasis-cli/module-info.java` and a `<dependency>` in `katabasis-cli/pom.xml`. Both are straightforward.

**Note:** adding picocli to `katabasis-core` is explicitly forbidden — the dependency belongs only in `katabasis-cli`.

## 5. Persistence & Recovery Gap Analysis

### Recovery flow

| Step | Description | Current state |
|------|-------------|---------------|
| 1 | Begin download | Works — `DownloadManager.download()` |
| 2 | Persist reliable checkpoints | **Partial** — store and coordinator exist but are NOT wired; ETag/partialPath/segments never populated |
| 3 | Shut down Katabasis | **Missing** — no `close()` / `shutdown()` API; `ExecutorService` never terminated |
| 4 | Restart application | **Missing** — no recovery entry point; `DownloadManagers.createDefault` has no overload accepting a store |
| 5 | Load recoverable snapshot | Works in isolation — `FileDownloadStateStore.findRecoverable()` returns snapshots with status `IN_PROGRESS` or `PAUSED` |
| 6 | Revalidate remote resource | Works in isolation — `HttpRangeSupport.probe()` and `rangeProbe()` are implemented; nothing calls them during recovery |
| 7 | Continue from confirmed offsets | **Missing** — HTTP strategies have no "resume from byte N" entry point; `DownloadRequest` has no offset field |

### Snapshot data gaps

`CheckpointCoordinator.build()` (line 251) always passes:
- `partialPath = null` → `effectivePartialPath()` falls back to `targetPath`
- `etag = null` → revalidation on restart cannot use `If-Range`
- `segments = List.of()` → segmented recovery is structurally impossible without this

Populating these fields requires access to `internal.*` state that never surfaces through `DownloadEvent`. The `DownloadStartedEvent` does not carry the ETag established during the range probe. `DownloadProgressEvent` does not carry segment boundaries.

**Three design choices for surfacing this data:**

1. **Enrich events**: add `etag` and `List<SegmentSnapshot>` to `DownloadStartedEvent`/`DownloadProgressEvent`. The coordinator receives everything it needs without accessing internal state. Clean separation. Moderate event API change.

2. **Callback into the coordinator from the strategy**: `HttpDownloadOrchestrator` calls a provided `Consumer<DownloadSnapshot>` after the range probe. The coordinator holds the snapshot directly. Tight coupling but no API change.

3. **Internal access via a richer executor context**: `DownloadExecutionContext` gains a snapshot sink; strategies write ETag and segment boundaries directly after negotiation. The coordinator subscribes to the sink. Moderate change to execution context.

**Recommendation: Option 1 (enrich events)** for the ETag (single value, available at download start). For segment boundaries, a dedicated `DownloadSegmentedStartedEvent` or an optional `segments` field on `DownloadStartedEvent` is sufficient.

## 7. Summary

**0.1 is correctly closed.** Concurrency enforcement is real; the placeholder schedulers are not needed and correctly identified as forward reserves.

**The storage layer is production-ready but not connected.** `FileDownloadStateStore`, `CheckpointCoordinator`, and `DownloadStateStores` are fully implemented, hardened, and tested. The only gap is wiring. `AGENTS-CORE.md` must be corrected.

**Three non-trivial gaps block end-to-end recovery:**
1. No `close()` on `DownloadManager` (K-0.2-T03)
2. ETag, `partialPath`, and segment boundaries never reach the checkpoint coordinator (K-0.2-T10)
3. No `recover()` API and no byte-offset resume path in HTTP strategies (K-0.2-T11)

**Recommended first implementation task: K-0.2-T03** — `DownloadManager.AutoCloseable` with graceful shutdown. It unblocks both the CLI track (a CLI that cannot be cleanly exited is not usable) and the persistence track (recovery semantics depend on shutdown behaviour). It is also the smallest of the three gaps.
