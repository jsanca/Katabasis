## 2. Findings

### LC-001 — `HttpDownloadStrategy.doDownloadAttempt`: InputStream not closed on status failure

**Severity:** Medium  
**Location:** `HttpDownloadStrategy.doDownloadAttempt()`, original structure

The response body was opened with `BodyHandlers.ofInputStream()`. The original code checked `isInvalidResponseStatus()` and threw `HttpDownloadStatusException` before the `try (InputStream …)` block opened. Any non-2xx response leaked the response body stream.

**Fix:** Wrap the response body in `try (InputStream inputStream = response.body())` immediately after `httpClient.send()`, then perform the status check inside the try block.

```java
// Before
final HttpResponse<InputStream> response = doGet(info);
if (isInvalidResponseStatus(response.statusCode())) {
    throw new HttpDownloadStatusException(info, response.statusCode()); // body not closed
}
try (InputStream inputStream = response.body(); OutputStream outputStream = …) { … }

// After
final HttpResponse<InputStream> response = doGet(info);
try (InputStream inputStream = response.body()) {
    if (isInvalidResponseStatus(response.statusCode())) {
        throw new HttpDownloadStatusException(info, response.statusCode()); // body closed
    }
    try (OutputStream outputStream = …) { … }
}
```

---

### LC-002 — `SegmentedHttpDownloadStrategy.doChunkAttempt`: InputStream not closed on status or header failure

**Severity:** Medium  
**Location:** `SegmentedHttpDownloadStrategy.doChunkAttempt()`, original structure

Same class of problem as LC-001. After `httpClient.send()`, the status check (`!= 206`) and `validateSegmentResponseHeaders` both ran before the `try (InputStream …)` opened. Any non-206 response or header validation failure leaked the stream.

**Fix:** Same structural change — `try (InputStream inputStream = response.body())` immediately wraps the `send()` result. The inner watchdog construction references the local variable `inputStream` (same object as `response.body()`).

## 3. Partial-File Policy

The two strategies handle partial-file cleanup differently by design.

| Strategy | On Failure | On Cancellation |
|---|---|---|
| `HttpDownloadStrategy` (single-stream) | File **retained** | File **retained** |
| `SegmentedHttpDownloadStrategy` | File **deleted** | File **deleted** |

**Rationale:**
- Single-stream partial bytes may be useful for manual recovery or a future resume implementation. Retaining them causes no silent corruption.
- Segmented partial files have missing or zero-filled (pre-allocated) segments and cannot be used or resumed without additional segment bookkeeping. Deletion prevents silent corruption from a file that appears complete but is not.

This policy is intentional. Do not change it without explicit request.

The following lifecycle properties were verified structurally (code inspection) and by integration test:

| Property | Mechanism | Verified |

| Registry entry always removed | `DownloadRegistry.remove()` called in same `finally` | Yes |
| Segmented subtasks always joined | `StructuredTaskScope` guarantees all forks complete before scope closes | Yes |
| Watchdog thread always stopped | `watchdog.close()` in `finally` block of read loop | Yes |
