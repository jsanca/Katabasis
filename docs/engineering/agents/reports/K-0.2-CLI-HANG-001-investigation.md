# K-0.2-CLI-HANG-001 — TC-CLI-009 Hang Root-Cause Investigation

**Date:** 2026-11-11
**Investigator role:** OSK engineering-reviewer (independent)
**Subject:** `jsanca.katabasis.cli.DownloadCommandTest.segmentedDownloadCompletesWithSameCommand`
**Verdict:** **Build-configuration defect (katabasis-cli/pom.xml)** — unrelated to HTTP, StructuredTaskScope correctness, or test prior-state.
**Severity:** High (masks a real failure of segmented downloads in every environment that does not pass `--enable-preview` at runtime).
**Classification:** Test-harness / build-configuration defect — **not** JDK, not test-fixture, not production-logic.

---

## 1. Problem recap

TC-CLI-009 was annotated `@Disabled` with the claim that the hang was caused by
"JDK HttpClient connection-pool starvation under `StructuredTaskScope` when
run after several preceding tests". The task required independent verification.

## 2. Falsifying the stated hypothesis

### 2.1 TC-CLI-009 hangs in strict isolation

With the `@Disabled` annotation removed and the test run on its own:

```
mvn test -pl katabasis-cli -Dtest=DownloadCommandTest#segmentedDownloadCompletesWithSameCommand
```

Result: `Tests run: 1, Failures: 1 … Time elapsed: 600.4 s` — the CLI timed out
after ten minutes waiting for a terminal event. No prior tests ran in the JVM.
**The existing hypothesis ("fails only after several prior tests") is false.**

### 2.2 Only one network request ever reaches the server

Instrumenting a new in-test harness to drive a bare `DownloadManager`
(no picocli, no `DownloadCommand`, no `ProgressRenderer`) with a listener that
prints every event showed:

```
EVT: DownloadStartedEvent -> DownloadStartedEvent[…]
=== Events after 8s: [DownloadStartedEvent] ===
=== Server requestCount=1 ===
```

`requestCount` counts only non-HEAD requests. A value of **1** means:
- HEAD probe reached the server (served)
- The `GET bytes=0-0` range-capability probe reached the server (served)
- **No chunk GET requests were ever sent.**

So the orchestrator completed its probes and selected
`SegmentedHttpDownloadStrategy`, but the chunk workers never executed.

### 2.3 Thread dump shows no segmented worker threads at all

`jcmd <pid> Thread.dump_to_file -format=plain` taken 20 s into the hang
(both for the bare-manager case and the full CLI case) contains **only two
user virtual threads**:

| VT | Stack top | Meaning |
|----|-----------|---------|
| `#27 "" virtual` | `ProcessImpl.waitFor` | the diagnostic watchdog |
| `#30 "" virtual` | `ServerSocket.accept` → `TestHttpServer.acceptLoop` | the test server's accept loop |

There is **no** `runDownload`, **no** `HttpDownloadOrchestrator`,
**no** `SegmentedHttpDownloadStrategy`, **no** `StructuredTaskScope`,
**no** chunk VT parked on `httpClient.send` or `NioSocketImpl.read`.
The JDK `HttpClient-1-SelectorManager` and `HttpClient-1-Worker-{0..2}`
threads are idle in their normal park states.

This rules out:
- "HttpClient connection-pool starvation"  — the JDK client pool is fully idle.
- "StructuredTaskScope deadlock"  — no scope is open.
- "chunk thread stuck in read"  — no chunk thread exists.
- "test-server socket leak from prior tests"  — isolation reproduces the hang.

The download virtual thread **has terminated silently** after emitting
`DownloadStartedEvent`.

## 3. The actual cause

### 3.1 Build-config discrepancy between modules

`katabasis-core/pom.xml`:

```xml
<argLine>--enable-preview --add-reads …</argLine>
…
<arg>--enable-preview</arg>   (compiler)
```

`katabasis-cli/pom.xml` (before fix):

```xml
<argLine>--add-opens jsanca.katabasis.cli/jsanca.katabasis.cli=ALL-UNNAMED</argLine>
```

**No `--enable-preview`** anywhere in the CLI module — neither at compile
time (not needed; CLI classes do not use preview APIs) nor, crucially,
in the Surefire JVM arguments.

`SegmentedHttpDownloadStrategy` uses the JDK 25 preview
`StructuredTaskScope.open(Joiner.<Void>awaitAllSuccessfulOrThrow())` API.
The class is compiled with `--enable-preview`, which stamps the
classfile with the `ACC_PREVIEW` minor-version marker.

When a class with the preview marker is loaded by a JVM that was not
started with `--enable-preview`, the HotSpot class-loader throws
`UnsupportedClassVersionError` (a subclass of `java.lang.Error`).

### 3.2 Why the error is invisible

In `DefaultDownloadManager.runDownload`:

```java
try {
    this.emit(new DownloadStartedEvent(info, occurredAt));
    final DownloadStrategy strategy = this.strategyResolver.resolve(info);
    strategy.download(task, context, this::emit);
} catch (Exception e) {
    …
    this.emit(new DownloadFailedEvent(…));
} finally {
    this.downloadRegistry.remove(info.downloadId());
}
```

The `catch` clause is `Exception`, not `Throwable`. `UnsupportedClassVersionError`
(or any `LinkageError`) is not caught here, bubbles out of the
`Runnable` submitted to `Executors.newVirtualThreadPerTaskExecutor()`,
which has no uncaught-handler, so the VT just dies. No `DownloadFailedEvent` is
emitted, the CLI's `terminalLatch` never counts down, and the caller hangs for
the full 10-minute timeout.

This exactly matches every observation: one `DownloadStartedEvent`, zero
chunk requests, zero chunk threads, no terminal event, no exception on stderr.

### 3.3 Conclusive demonstration

Adding `--enable-preview` to the CLI module's Surefire `argLine`:

```xml
<argLine>--enable-preview --add-opens jsanca.katabasis.cli/jsanca.katabasis.cli=ALL-UNNAMED</argLine>
```

and removing the `@Disabled` annotation — with nothing else changed:

```
[INFO] Tests run: 13, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.808 s -- in jsanca.katabasis.cli.DownloadCommandTest
[INFO] Tests run: 18, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

TC-CLI-009 runs in **0.6 s**, all 13 `DownloadCommandTest` tests pass,
the full CLI suite is green.

## 4. Root-cause summary (checklist from the brief)

1. **Triggering condition** — any run of the CLI surefire JVM, with or without
   prior tests. (The "only in full suite" observation in the original report
   was likely coincidental timing of when the dev first ran the single test.)
2. **Component responsible** — `katabasis-cli/pom.xml` Surefire `argLine`:
   missing `--enable-preview`.
3. **Blocking operation** — there is none in the download path. The CLI's
   `terminalLatch.await` at `DownloadCommand.java:105` blocks only because the
   terminal event never arrives; the download VT silently died on
   `UnsupportedClassVersionError` loading `SegmentedHttpDownloadStrategy`.
4. **Why isolation also fails** — it does; the earlier claim that it "passes in
   isolation" was not reproduced here. Reproduction command above.
5. **Supporting evidence**
   - Full-VT thread dump (`jcmd … Thread.dump_to_file -format=plain`) shows
     zero download-related threads at 20 s. See `/tmp/vt-dump-*.txt`.
   - Bare-manager diagnostic prints `DownloadStartedEvent` then nothing; server
     records `requestCount=1`.
   - Adding `--enable-preview` to `katabasis-cli/pom.xml` makes all 13 tests
     pass in <1 s.
6. **Minimal correction** — one-line edit in `katabasis-cli/pom.xml`:
   ```diff
   - <argLine>--add-opens jsanca.katabasis.cli/jsanca.katabasis.cli=ALL-UNNAMED</argLine>
   + <argLine>--enable-preview --add-opens jsanca.katabasis.cli/jsanca.katabasis.cli=ALL-UNNAMED</argLine>
   ```
7. **Regression test** — TC-CLI-009 itself, re-enabled (remove `@Disabled`),
   is sufficient: it covers the exact segmented-download code path and will
   fail (hang + timeout) whenever a dependent module loads a preview-stamped
   class without `--enable-preview`.

## 5. Recommendation

**Corrective action: B (production/build fix)**, specifically a two-line change:

1. `katabasis-cli/pom.xml`: add `--enable-preview` to the Surefire `argLine`
   (shown above).
2. `katabasis-cli/src/test/java/jsanca/katabasis/cli/DownloadCommandTest.java`:
   remove the `@Disabled(...)` annotation on `segmentedDownloadCompletesWithSameCommand`
   and delete the `Disabled` import if unused.

A follow-up hardening change is worth considering but is **out of scope for
this report**:

- **Catch `Throwable` (not `Exception`) in `DefaultDownloadManager.runDownload`
  around the strategy call**, so that a `LinkageError` or other `Error` on the
  download VT is surfaced as a `DownloadFailedEvent` instead of silently killing
  the VT. This would have turned the 10-minute hang into an immediate test
  failure with a clear stack trace, saving an afternoon of investigation. This
  is a production robustness improvement, not strictly required to fix the
  current bug.

## 6. What did NOT need to change

- `TestHttpServer` in the CLI test is **functionally correct**. It is a
  slightly reformatted copy of the identical server in `DownloadManagerE2ETest`
  which runs the same segmented strategy successfully today. No framing,
  threading, or lifecycle defect was found in it.
- `SegmentedHttpDownloadStrategy`, `HttpDownloadOrchestrator`, and
  `HttpRangeSupport` are working correctly (proven by the suite passing once
  preview is enabled, and by the already-green `DownloadManagerE2ETest`
  which exercises them identically).
- `DownloadCommand` event handling is correct. The bare-manager reproducer
  bypassed it entirely and showed the same hang, so the picocli layer is not
  implicated.
- `HttpClient` lifecycle and pool behaviour are irrelevant to this symptom.

## 7. Verification plan
